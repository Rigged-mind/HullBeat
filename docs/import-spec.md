# Специфікація імпортера

Головний технічний виклик проєкту. Вхід — таблиці, які кожен власник вів по-своєму
десятиліттями. Мета — **не втратити жодного рядка**, навіть якщо ми його не зрозуміли.

Емпірика по реальних layout'ах — [forum-evidence.md](forum-evidence.md), п.4.

## 1. Принцип

**Не вгадувати. Класифікувати → запропонувати → підтвердити.**

Автоматичний парсер, який «сам розбереться», неможливий: схеми у власників різні за
визначенням («I like my own personal one, but I wouldn't be surprised if no one else did»).
Тому цільові показники такі:

| Метрика | Ціль |
|---|---|
| Колонок змаплено автоматично | ~80% |
| Дій користувача на решту | ≤ 3 дотики на колонку |
| **Втрачених рядків** | **0%** — завжди |
| Провалених імпортів | 0 — деградуємо, а не падаємо |

Останні два рядки — головні. Імпорт **не має права завершитись помилкою**.
Нерозпізнаний рядок стає записом-нотаткою з повним вихідним текстом, який шукається
через FTS. Це гірше за структурований запис, але незрівнянно краще за «формат не підтримується».

## 2. Виміри варіативності, які треба тримати

Зібрано з реальних описів на форумах плюс звичайна практика.

### 2.1. Формат файлу
`.xlsx`, `.csv`, `.tsv`, `.ods`, експорт із Google Sheets.
`.xls` (старий бінарний BIFF) — рідкість, просимо перезберегти.
`.numbers` — не підтримуємо, просимо експорт.

### 2.2. Кодування й розділювачі
UTF-8, UTF-8 з BOM, cp1251, cp1252, ISO-8859-1.
Розділювач: `,` `;` `\t` `|`. У європейських локалях `;` — норма, бо кома зайнята дробовою частиною.
Лапки за RFC 4180 + невалідні варіанти (неекранована лапка всередині поля).

### 2.3. Структура аркуша
- Плоска таблиця з шапкою в 1-му рядку
- **Матриця: роки в шапці** (найпоширеніше у досвідчених)
- Титульні рядки над шапкою («Maintenance log — Stella Maris», порожній рядок, потім шапка)
- Об'єднані клітинки в шапці, дворядкова шапка
- Рядки-підсумки внизу (`TOTAL`, `Σ`)
- Кілька незалежних таблиць на одному аркуші, розділених порожніми рядками
- Багатовкладкова книга, де вкладки — це категорії (fuel / winterization / spring
  commissioning / parts / to-do / admin reminders)
- Багатовкладкова книга, де вкладки — це **роки**
- **Один файл на рік** → кілька файлів мусять зливатися в один журнал

### 2.4. Назви колонок (потрібні словники синонімів)
- дата: Date, Datum, Data, Fecha, Дата, When, Day
- опис: Task, Task performed, Work, Job, Description, What I did, Arbeit, Lavoro
- мотогодини: Hours, Hrs, H, Engine hours, Eng hrs, Motorstunden, Ore motore, Моточаси
- вартість: Cost, Amount, Price, Total, €, $, Kosten, Costo
- виконавець: By, Who, Technician, Mechanic, Yard
- запчастина: Part, Part number, P/N, Parts used, Teil
- нотатки: Notes, Remarks, Comments, Anmerkungen

Мови для v1: EN, DE, FR, IT, ES, HR, UA. Це географія власників 5–15 м.

### 2.5. Формати дат — найбільше джерело тихих помилок
- `MM/DD/YYYY` проти `DD/MM/YYYY` — **неоднозначно**; див. п.4.3
- `YYYY-MM-DD`, `DD.MM.YYYY`, `DD-MMM-YY` (`14-Apr-19`)
- Excel serial number (`43570`) — і різні епохи (1900 проти 1904 у старих Mac-файлах)
- Тільки рік: `2019`
- Сезон: `Spring 2019`, `Haul-out 2020`, `Winter 19/20`
- Місяць: `May-19`, `05/19`

### 2.6. Числа й одиниці
- `1 234,56` проти `1,234.56` проти `1234.56`
- Символи валют і суфікси: `$450`, `450 EUR`, `£45.20`
- Неточні значення: `~50`, `50+`, `50-60`, `n/a`, `-`, `?`, `TBD`
- Одиниці наробітку: години / милі / nm / km — і різні для різних вузлів
- Валюти змішані в одному файлі

### 2.7. Семантика клітинок
- Одна клітинка = кілька робіт: `oil + filters + impeller`
- Клітинка = позначка, а не дата: `X`, `✓`, `done`, `yes`
- У матриці клітинка = дата, а колонка = рік → **дата й рік можуть конфліктувати**
- Номер деталі всередині вільного тексту: `changed impeller (Jabsco 17937-0001)`
- Посилання на інвойс у колонці нотаток

### 2.8. ⚠️ Колір клітинки — це дані
Досвідчені власники кодують стан умовним форматуванням:
«a category **turns yellow or red** when a condition is met».

Тому заливку читати обов'язково: червоний/жовтий фон у рядку — сигнал «прострочено /
настає», навіть якщо текстом цього немає. Використовувати як підказку при мапінгу
статусу, не як істину.

## 3. Конвейер

```
[1] SNIFF      формат, кодування, розділювач, epoch дат
      ↓
[2] GRID       нормалізація в матрицю клітинок: value + type + numFmt + fillColor
      ↓
[3] REGIONS    пошук таблиць на аркуші: титули, шапка, тіло, підсумки
      ↓
[4] CLASSIFY   форма layout'у: FLAT | MATRIX | KEYVALUE | UNKNOWN
      ↓
[5] MAP        оцінка кандидатів «колонка → поле» з довірою
      ↓
[6] PREVIEW    користувач бачить перші 20 записів і правки; підтверджує
      ↓
[7] STAGE      запис у import_row (raw_json) + парсинг у чернетки
      ↓
[8] COMMIT     створення ServiceRecord / MeterReading / InventoryItem з provenance
```

Кроки 1–5 виконуються без участі людини. Крок 6 — єдина обов'язкова взаємодія.

### Крок 4: як розпізнати матрицю

Ознаки, всі мусять зійтися:
1. У рядку-шапці ≥ 3 клітинки парсяться як рік у діапазоні 1980–2035
2. Перша колонка містить переважно текстові мітки, не дати й не числа
3. Тіло таблиці — переважно дати, порожні клітинки або позначки

Якщо так — розгортаємо:
```
для кожної колонки-року Y:
  для кожного рядка-задачі T:
    якщо клітинка (T,Y) не порожня:
      ServiceRecord(
        опис        = мітка з першої колонки рядка T,
        дата        = розібрана з клітинки; якщо це X/✓ → 1 липня року Y, точність=YEAR,
        мотогодини  = значення з «рядка мотогодин» для колонки Y, якщо є,
        джерело     = (аркуш, рядок T, колонка Y)
      )
```
Повторна колонка з тим самим роком («I add another column repeating the year») обробляється
природно, бо кожна колонка розгортається окремо.

### Крок 5: як оцінювати мапінг

Дві незалежні оцінки на кожну пару (колонка, поле), потім добуток:

**За назвою** — нормалізація (lowercase, зняти пунктуацію й діакритику) → точний збіг
зі словником синонімів = 1.0, збіг за підрядком = 0.6, відстань Левенштейна ≤ 2 = 0.4.

**За значеннями** — частка клітинок, що проходять валідатор поля:
- `дата`: частка, що парсяться хоч одним форматом
- `мотогодини`: числові **і** переважно неспадні по часу (лічильник не крутиться назад)
- `вартість`: числові з валютою або в розумному діапазоні
- `опис`: текстові, середня довжина > 8 символів, висока унікальність
- `виконавець`: текстові, **низька** унікальність (кілька повторюваних імен)

Автозастосування при добутку ≥ 0.75. Від 0.4 до 0.75 — пропозиція, підсвічена як
«перевірте». Нижче 0.4 — питаємо.

## 4. Правила, які врятують від тихих помилок

### 4.1. Ніколи не парсити дату по одній клітинці
Рішення приймається **на рівні колонки**: пробуємо кожен формат-кандидат на всій колонці,
перемагає той, що дає найбільше успішних розборів. Потім застосовуємо його до всіх.

### 4.2. Точність дати — окреме поле
`date_precision: DAY | MONTH | YEAR | SEASON`.
«Spring 2019» — це не 1 березня 2019, це весна 2019. Прогноз наробітку мусить знати,
що ця точка нечітка, і не будувати на ній тренд.

### 4.3. Неоднозначні дати — вирішувати по колонці, потім питати
Скан колонки: якщо хоч одне значення має першу компоненту > 12 → це `DD/MM`.
Якщо друга > 12 → `MM/DD`. Якщо **всі** значення ≤ 12 — неоднозначно, і тоді питаємо
прямо, показавши приклад: «`03/04/2019` — це 3 квітня чи 4 березня?».
Дефолт за локаллю файлу — але з видимим запитом, не молчки.

### 4.4. Дублікати при повторному імпорті
Ключ дедуплікації: `hash(дата, нормалізований опис, мотогодини)`.
Люди зберігають «копію на кожен рік», тож повторний імпорт оновленого файла — норма,
а не виняток. Показуємо: «120 записів, з них 98 уже є → пропустити / оновити / додати».

### 4.5. Provenance назавжди
Кожен запис знає, звідки прийшов: `import_session_id`, аркуш, рядок, колонка.
Це дає (а) кнопку «відкотити цей імпорт цілком», (б) можливість показати користувачу
вихідну клітинку, коли він не розуміє, звідки взявся запис.

### 4.6. Зберігати сирий рядок вічно
`import_row.raw_json` не видаляється після коміту. Наслідок: коли парсер поліпшиться,
можна **перепарсити старі імпорти без файла й без користувача**. Це також страховка
від власних багів на етапі, коли продукт молодий.

### 4.7. Мапінг як пресет
Підтверджений мапінг зберігається за відпечатком шапки (`hash` нормалізованих назв колонок).
Наступний файл з такою ж шапкою — імпорт в один дотик. Це і покриває кейс
«файл на кожен рік».

## 5. Бібліотека відомих шаблонів

Окрім евристик — набір готових розпізнавачів за відпечатком шапки, які дають
100% мапінг без питань.

### 5.0. Наш еталонний шаблон — вхід №1

`template/Boat maintenance log.xlsx`, генерується `tools/make_template.py`.

Розпізнається **не за шапкою, а за маркером**: прихований аркуш `_meta`,
клітинка `B1` = `HULLBEAT-TEMPLATE`, `B2` = версія. Це надійніше за відпечаток
колонок, бо власник майже напевно щось перейменує або додасть свої колонки —
і має мати на це право.

Аркуші й цільові сутності:

| Аркуш | Куди лягає |
|---|---|
| `Service log` | `ServiceRecord` (+ `MeterReading`, якщо заповнені мотогодини) |
| `Hours & miles` | `MeterReading` |
| `Schedule` | `ServiceSchedule` |
| `Spec sheet` | `Component.spec_json` (пари ключ-значення) |
| `Inventory` | `Part` + `InventoryItem` + `Location` |
| `Documents` | `Document` з `expires_on` |
| `_meta` | не імпортується |

Колонки `Next due` і `Status` — обчислювані, **при імпорті ігноруються**:
їх рахує рушій, а не таблиця. Читаємо значення, не формули (п.8).

Поведінка при поламаному маркері (аркуш видалили, колонки перейменували) —
звичайний шлях через евристики й мапінг. Шаблон дає швидкий вхід, а не єдиний.

### 5.1. Чужі шаблони

- **MV Dirona** — найчастіше згадуваний референс на форумах
- **astrolabesailing.com (Viki Moore)** — «The Ultimate Boating Spreadsheet»
- **Експорти конкурентів**: Vessly (CSV), Bavyn, VesselMinder, Boating Suite,
  YachtWave — щоб забрати користувача, який тікає від них
- Типові шаблони з safe-skipper, thevanabondtales

Кожен — просто JSON-опис у assets: відпечаток шапки + готова карта полів + layout.
Дешево додавати, дає найкращий перший досвід.

## 6. Реалізація на Android

### 6.1. XLSX без Apache POI
POI на Android — це десятки тисяч методів, роздутий APK і проблеми з dex.
**XLSX — це просто zip з XML.** Читаємо `ZipInputStream` + `XmlPullParser`
(обидва в платформі, нуль залежностей):

- `xl/workbook.xml` → список аркушів
- `xl/sharedStrings.xml` → таблиця рядків
- `xl/styles.xml` → `numFmt` (щоб відрізнити дату від числа) і `fill` (колір, п.2.8)
- `xl/worksheets/sheetN.xml` → клітинки потоково

Це ~300–400 рядків, streaming (великі файли не в пам'яті) і повний контроль
над тим, що нам треба — включно з кольором заливки, який POI-обгортки часто ховають.

### 6.2. CSV
Власний RFC 4180 парсер зі сніфером розділювача й кодування (BOM, потім евристика
за частотою байтів). Або `kotlin-csv`, якщо не хочеться писати сніфер — але сніфер
однаково потрібен.

### 6.3. ODS
Той самий підхід: zip + `content.xml`. Додати після MVP.

### 6.4. Таблиці БД імпорту

```
ImportSession   id, file_name, file_hash, format, layout, mapping_json,
                sheet_count, row_count, status, created_at
ImportRow       id, session_id, sheet, row_index, col_index, raw_json,
                parse_status, target_type, target_id
TemplatePreset  id, header_fingerprint, name, mapping_json, layout, is_builtin
```

## 7. UX preview — те, що вирішує довіру

Екран підтвердження мусить показувати:

1. **Що ми зрозуміли**: «Знайдено матрицю: 14 задач × 7 років = 63 записи»
2. **Таблицю мапінгу** з відсотком довіри й можливістю змінити поле в один тап
3. **Перші 20 записів як вони виглядатимуть у застосунку** — не сирі рядки
4. **Що не зрозуміли**: «11 рядків збережемо як нотатки з повним текстом» —
   з можливістю розкрити й перевірити
5. Кнопку **«Скасувати цей імпорт»**, доступну й після коміту

Пункт 4 — критичний для довіри. Аудиторія боїться втрати даних; чесне
«ці 11 ми не розібрали, але зберегли дослівно» працює краще за приховану втрату.

## 8. Чого свідомо не робимо

- **Не використовуємо LLM у v1.** Спокусливо, але: потрібна мережа (а ми офлайн-first),
  дані власника йдуть на чужий сервер (а ми обіцяємо протилежне), і це витрати
  на кожного користувача при разовій оплаті. Евристики + підтвердження покривають
  ту саму задачу детерміновано. Можливо пізніше — локальною моделлю або як опція.
- Не намагаємось розібрати PDF-и й сканы журналів. Фото → OCR → нотатка, і достатньо.
- Не імпортуємо формули, лише обчислені значення.
