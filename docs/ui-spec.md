# Інтерфейс: каркас

Складено з наявних доказів ([forum-evidence.md](forum-evidence.md), [competitors.md](competitors.md)).

**Оновлено 2026-09-05** за 46 скріншотами Bavyn 1.0.0, Vessly 1.4.0 і
Boat Maintenance Planner 1.3.6 — розбір у **[competitor-ux.md](competitor-ux.md)**.
Каркас підтвердився; додано вісім запозичених патернів (див. п.7.1) і перелік
антипатернів, кожен з яких бачив на живому екрані.
Місця, де ми ще вгадуємо, позначені ⚠️ і винесені в п.9 як список перевірки на човні.

## 1. Умови експлуатації диктують усе

Це не офісний застосунок. Його відкривають:

| Ситуація | Наслідок для UI |
|---|---|
| Яскраве сонце на палубі | Максимальний контраст, крупний шрифт. **У сонці потрібна світла тема**, не темна |
| Темний моторний відсік | Темна тема, ліхтарик не зайнятий рукою |
| Руки мокрі, брудні або в рукавичках | Ціль дотику **≥ 56 dp**, великі проміжки, жодних дрібних іконок |
| Одна рука зайнята (тримається за що завгодно) | Первинні дії — **у нижній третині екрана**, у зоні великого пальця |
| Взимку пальці не слухаються | Жодних точних жестів, довгих натискань як єдиного способу, драг-н-дропу |
| Звʼязку немає | **Ніколи не показувати спінер очікування мережі й помилку «немає зʼєднання»** |
| Стоїть у магазині запчастин | Паспорт вузла має бути за 2 дотики, не за 5 |
| Робить кілька робіт за один візит | Один візит = кілька записів, без повторного проходу по формі |

Конкретні числа: базовий шрифт 16sp, ключові числа 28–32sp, первинна кнопка
висотою 56dp на всю ширину мінус поля, мінімальний проміжок між клікабельними 12dp.

Окремий перемикач **«Яскраве сонце»** — примусово світла тема + контраст + шрифт +1 крок.
Не покладатись лише на системну тему.

## 2. Архітектура навігації

Пряма скарга на конкурента: «you have to go between **a lot of tabs** to get the info
that you want». Тому правило: **до будь-якого запису — максимум 3 дотики.**

Нижня панель, рівно 4 розділи (більше — розмиває):

```
[ Зараз ]   [ Човен ]   [ Журнал ]   [ Склад ]
                  ( + )  ← FAB, завжди
```

- **Зараз** — що горить. Стартовий екран завжди.
- **Човен** — дерево категорій і вузлів (каталог із taxonomy.md).
- **Журнал** — вся історія, з пошуком.
- **Склад** — запчастини за локаціями.

Пошук — іконка в верхній панелі **на кожному екрані**, плюс закріплене поле в Журналі
й Складі. Це відповідь на «fails on fundamental search functionality» у лідера категорії.

Дані живуть у меню верхньої панелі, не займають вкладку.

### ⚠️ Чеклісти: частота вирішує місце, і вона більше не одна

Спершу тут стояло «чеклісти живуть у меню» — і це було правильно, доки всі
вони були сезонні. Потім додався **«Перед виходом»**, який працює щоразу, коли
човен відходить від причалу. Щотижнева річ за меню не ховається.

| Список | Частота | Де живе |
|---|---|---|
| Консервація · Розконсервація | 2 рази на рік | меню верхньої панелі |
| Перевірка безпеки | раз на рік | меню + сама зʼявляється в «Зараз» за розкладом |
| **Перед виходом** | **щовиходу** | **чип на «Зараз», над списком** |

```
2 прострочено   3 скоро          ( ⛵ Вихід у море → перевірка )
```

Чип не займає вкладку й не конкурує з простроченим ТО за увагу: він над
списком, вужчий за картку, і зникає, коли перевірку пройдено сьогодні.

**Вкладок лишається чотири**, і це ті чотири місця, де живуть дані:
`Зараз · Човен · Журнал · Склад`. Чеклісти — не місце, а процедура; вона
приходить туди, де в ній є потреба.

⚠️ **У прототипі навігація інша**: `Зараз · Чеклісти · Вузол · Журнал`. Це
**будівельні ліси, не рішення**. «Вузол» стоїть замість дерева «Човен», якого
ще немає, а «Чеклісти» отримали вкладку тільки тому, що без дерева їх ніде
причепити. Розходження назване тут навмисно — щоб воно не стало дизайном
молчанням.

## 3. Екран «Зараз» — головний

Не архів, а список того, що горить.

```
┌─────────────────────────────────┐
│ Stella Maris ▾            🔍 ⋮ │  ← перемикач суден, якщо їх кілька
├─────────────────────────────────┤
│  3 прострочено · 2 скоро        │  ← смуга статусу, крупно
├─────────────────────────────────┤
│ ● Імпелер забортної помпи       │  ← червона крапка
│   Двигун головний               │
│   247 з 250 мотогодин           │  ← ЧОМУ воно горить
│              ┌────────────────┐ │
│              │    Зроблено    │ │  ← 56dp, у зоні пальця
│              └────────────────┘ │
├─────────────────────────────────┤
│ ◐ Аноди корпусні                │
│   Корпус і підводна частина     │
│   прогноз: ~14 серпня            │  ← прогноз, а не «прострочено на X»
│              ┌────────────────┐ │
│              │    Зроблено    │ │
│              └────────────────┘ │
└─────────────────────────────────┘
                            ( + )
```

Сортування: прострочене → настає → далі. При однаковій простроченості вгору йде
`criticality: high` з каталогу (імпелер важливіший за полірування).

**Кнопка «Зроблено» просто на картці** — це і є той «запис у два дотики».
Другий дотик — «Зберегти» в аркуші, що виїжджає (п.4).

Тап по картці (не по кнопці) → картка вузла.

⚠️ Відкрите питання: чи потрібен окремий фільтр «показати все, включно з не терміновим».
Схиляюсь до так, але як чип угорі, не як вкладка.

## 4. Швидкий запис — нижній аркуш, не окремий екран

Найважливіший елемент продукту. Викликається кнопкою «Зроблено», з FAB або
**прямо зі сповіщення, без відкриття застосунку**.

```
┌───────────────────────────────────────────────┐
│ Імпелер забортної помпи                       │
│ ДАТА       ┌───────────────────────────┐      │
│            │ Сьогодні, 5 вересня     ▾ │      │
│            └───────────────────────────┘      │
│ РОБОТА     ┌───────────────────────────┐      │
│            │ Планове ТО              ▾ │      │
│            └───────────────────────────┘      │
│ ЛІЧИЛЬНИК  ┌───────────────────────┐        ✕ │  ← додано плиткою
│            │ 512               год │          │
│            └───────────────────────┘          │
│            Скільки годин на лічильнику зараз. │  ← підказка
│            З цього рахується прогноз.         │
│                                               │
│ ДОДАТИ ЗА БАЖАННЯМ — усе нижче не обовʼязкове │
│ (✓ Мотогодини) (+ Деталь) (+ Вартість)        │
│ (+ Фото) (+ Нотатка)                          │
│                                               │
│        ┌────────────────────┐                 │
│        │      Зберегти      │                 │
│        └────────────────────┘                 │
└───────────────────────────────────────────────┘
```

#### ⚠️ Аркуш типізований: набір полів визначає сам вузол

Однаковий аркуш для всього — помилка, і на прототипі вона стала очевидною:
у записі про **страховку** пропонувались «Мотогодини» і «Деталь».

Правило не список винятків, а одне речення:

> **Аркуш питає рівно те, що потрібно, аби пункт перестав бути простроченим.**

Що з цього випливає:

| Що записуємо | Обовʼязкове | Чипи | Кнопка |
|---|---|---|---|
| Вузол із годинним інтервалом | дата | **Мотогодини** · Деталь · Вартість · Фото · Нотатка | Зроблено |
| Вузол із календарним інтервалом | дата | Деталь · Вартість · Фото · Нотатка | Зроблено |
| Вузол із `expiresOn` (пліт, фальшфейєри, вогнегасники) | дата + **новий термін** | Фото сертифіката · Вартість · Нотатка | Продовжено |
| `Document` (страховка, реєстрація, інспекція) | **новий термін дії** | Скан поліса · Номер полісу · Вартість · Нотатка | Продовжено |
| Показник лічильника | значення | Фото лічильника · Нотатка | Записати |
| Пункт чекліста | — | Нотатка | Готово |

**Мотогодин немає там, де немає лічильника. «Деталі» немає там, де нічого не міняють.**

**Новий термін — поле обовʼязкове, а не чип.** Це головна частина правки.
Для документа й для вузла з `expiresOn` записати «зроблено сьогодні» недостатньо:
модель тримає `expiresOn`, і без нової дати пункт або одразу знову стане червоним,
або зникне зі списку з неправильною датою. Тому дата виносится в тіло аркуша
поруч із датою виконання, а «Зберегти» неактивне, доки її не введено.

**Дієслово на кнопці відповідає дії.** Страховку не «роблять» — її продовжують.
Пліт не «роблять» — його здають на сервіс і отримують новий термін.
`Зроблено` · `Продовжено` · `Записати` · `Готово`.

#### ⚠️ Відкладене — це не робота, і кнопка на ньому не веде в аркуш

`Повернути` стояло тут як пʼяте дієслово в тому ж ряду — і це була помилка
двічі.

**Слово не відповідало ні на «що», ні на «куди».** Питання власника було
дослівним: *«Повернути. Це про що?»* Повернути гроші? Кіль на місце? Слово без
доповнення в інтерфейсі не працює.

**Гірше: кнопка відкривала аркуш запису роботи.** Тобто скасування відкладення
оброблялося як виконана робота — з датою, типом роботи й плитками. Але зняти
відкладення **не означає нічого зробити**: вузол просто повертається в список
у тому стані, в якому був. Аркуш тут не потрібен взагалі.

Тепер:

| | Було | Стало |
|---|---|---|
| Напис | `Повернути` | `Скасувати відкладення` |
| Дія | відкривався аркуш запису | картка змінюється **на місці** |
| Наслідок | — | ◇ → ●, напис стає `Зроблено`, снекбар «Повернуто в список» |

**Відкладення глушить нагадування, але не стирає факт.** Раніше картка
показувала лише «відкладено до підйому · жовтень» — і те, що вузол насправді
прострочений на 41 день, зникало з очей. Тепер рядок несе обидва:
«**прострочено 41 день · відкладено до підйому (жовтень)**». Це прямий наслідок
правила з п.8: колір і стан не єдиний носій сенсу, а відкладення — не
скасування проблеми, а домовленість про час.

#### ⚠️ Дірка, яку відкрило наступне питання: відкласти не було як

> *«Якщо користувач скасовує відтерміноване обслуговування, а потім змінює
> думку та все ж таки хоче відтермінувати — як це відбувається?»*

Ніяк. Я збудував лише зворотний напрямок: відкладене можна було повернути, але
**поставити відкладення не було звідки**. У даних стан `DEFERRED` існував, у
`DueCalculator` оброблявся, а в інтерфейсі його могла створити лише я — вписавши
руками в демо-дані. Класична однобока дія.

І другий бік тієї ж дірки: **«Скасувати» в снекбарі нічого не скасовував** —
просто ховав снекбар. Тобто помилковий дотик був незворотний, попри правило
п.8 «скасування замість підтвердження».

**Кожна картка, яка чогось просить, має другу відповідь.** Перша — «Зроблено»,
друга — «не можу зараз». Друга живе тихим текстовим рядком під головною кнопкою:
44 px висоти, підкреслене слово, вага муted. Видима кнопка, як вимагає п.8, але
не другий темний прямокутник.

| Стан | Головна кнопка | Тихий рядок під нею |
|---|---|---|
| прострочено · скоро | `Зроблено` / `Продовжено` | Не можу зараз — <u>відкласти</u> |
| відкладено | `Зроблено` | <u>Скасувати відкладення</u> |
| норма | `Зроблено` | — |

**Рядка немає на здорових вузлах.** Відкласти те, що настане у квітні 2027,
безглуздо — пропозиція зʼявляється рівно тоді, коли вузол справді чогось просить.

**Відкладене теж можна зробити.** Головна кнопка на відкладеній картці лишається
`Зроблено`: підйом могли призначити раніше, ніж планували.

**Аркуш відкладення питає дві речі:**

- `ДОКИ` — список: *До підйому — жовтень · На місяць · До весни · Обрати дату…*
- `ЧОМУ` — вільний текст, не обовʼязково.
  Підказка: «Через місяць ви навряд чи памʼятатимете, чому відклали саме це.»

І одне речення пояснює наслідок: «Пункт зникне з «Зараз» і **повернеться сам** у
вказаний час. Прострочення нікуди не дінеться — воно й далі буде написане на
картці.»

**Обидва напрямки — це один запис із поміняними полями**, тому обидва
відкатуються. Снекбар тепер тримає **знімок стану до зміни** й повертає його
дослівно: `Відкладено до весни` → «Скасувати» → знову `прострочено 41 день`.
Вікно — 5 секунд, як і для запису роботи.

Тобто відповідь на питання власника: **три шляхи, і жоден не тупиковий.**
Відразу — «Скасувати» в снекбарі. Пізніше — той самий тихий рядок, який тепер
пропонує «відкласти». А якщо відклали не на той строк — відкласти ще раз із
іншою датою, стара просто заміщується.

Це саме той клас помилки, що й `bilge_alarm` у термінології: формулювання
виглядало розумно, поки не поставили поруч із реальним предметом.

#### ⚠️ Плитка має додавати рядок, а не підсвічуватись

Друга помилка, яку видно лише на живому прототипі. Ряд плиток
«Фото · Мотогодини · Вартість · Нотатка · Деталь» стояв **без заголовка**, а
натискання плитки лише міняло її колір. Питання власника було дослівним:
*«що там до чого?»* — і воно правильне.

Причин було три, і всі про підпис, а не про логіку:

**Рядки показували значення без назви.** «Сьогодні, 5 вересня» ще вгадується.
«Планове ТО» — ні: незрозуміло, це назва роботи, її тип чи стан вузла. Тепер
кожен рядок має підпис у лівій колонці: `ДАТА · РОБОТА · ЛІЧИЛЬНИК · ПОСТАВИВ`.

**Плитки без заголовка читаються як фільтри.** Однакові пігулки в ряд — це
патерн фільтра, а не введення. Тепер над ними стоїть
«**Додати за бажанням — усе нижче не обовʼязкове**», що одночасно називає
призначення і знімає тиск: аркуш можна закрити одним «Зберегти».

**Натискання нічого не робило.** Плитка ставала зеленою — і все. Тепер вона
**вставляє рядок** у тіло аркуша, а `+` міняється на `✓`. Механіка пояснює себе
за один дотик.

#### ⚠️⚠️ Але цього виявилось замало: значення мають бути полями, а не текстом

Друга ітерація з тим самим власником. Формулювання було точним:

> *«Крім вартості та мотогодин — незрозуміло. І то не видно, як змінити
> значення. Що поставив — це про що?»*

Дві окремі речі, і обидві мої.

**Значення виглядали як факт, а не як поле.** Я малював текст із дрібним сірим
«змінити» збоку. Але **факт на екрані ніхто не намагається натиснути** — сірий
підпис читається як пояснення, а не як кнопка. Так само рядок, доданий плиткою,
приходив уже заповненим («Jabsco 17937-0001»): це виглядало як довідка з
каталогу, а не як щось, що я маю ввести сам.

Виправлення просте й нудне: **справжні елементи вводу з видимою межею.**
Дата й тип роботи — `select` зі списком (це вибір із кількох, а не текст).
Решта — порожній `input` із плейсхолдером і одиницею праворуч (`512` `год`).
Порожнє поле з підказкою всередині — єдиний стан, який неможливо сплутати з
готовим значенням.

**Назва поля не пояснює його призначення, і не має.** «Що поставив» — питання
без контексту. Але й будь-який інший іменник програв би: проблема не в слові.
Тому під кожним доданим полем стоїть **один рядок про те, навіщо воно**:

| Плитка | Рядок | Плейсхолдер | Підказка під полем |
|---|---|---|---|
| + Мотогодини | `ЛІЧИЛЬНИК` | `512` год | Скільки годин на лічильнику **зараз**. З цього рахується прогноз. |
| + Деталь | `ДЕТАЛЬ` | `Jabsco 17937-0001` | Що саме ви поставили — артикул або назва. Щоб наступного разу купити те саме й не шукати заново. |
| + Вартість | `ВАРТІСТЬ` | `1240` ₴ | Скільки коштувало. Підсумок за сезон буде в журналі. |
| + Фото | `ФОТО` | Додати знімок | Знята деталь або місце роботи. Через рік це єдиний спосіб порівняти знос. |
| + Нотатка | `НОТАТКА` | `Лопаті цілі, корпус чистий` | Що ви помітили: стан, знос, на що глянути наступного разу. |
| + Номер полісу | `ПОЛІС №` | `UA-2026-114857` | Номер із бланка — щоб не діставати сам поліс. |

Підказка зʼявляється **під полем, у момент, коли поле додали** — тобто рівно
там, де виникає питання. Загальна легенда десь угорі цю роботу не виконує:
її треба подумки звʼязати назад із назвою, а ніхто цього не робить.

Назву **повернуто на «Деталь»**. Спроба уточнити її до «Що поставив» була
хибним ходом: я лікував словом те, що лікується підказкою, і зробив плитку
довшою без виграшу в ясності.

**Обовʼязкове поле теж отримало підказку** — і саме воно її потребує найбільше:
*«Без нової дати пункт завтра знову стане червоним.»* Це відповідь на питання
«а нащо ви взагалі просите дату, я ж уже натиснув „Продовжено“».

Правила:

- Обовʼязкові лише дата й вузол — **обидва вже заповнені**. Тобто мінімум = один дотик «Зберегти».
- Плитки додають рядок **усередині аркуша**, не ведуть на інший екран.
  Повторний дотик по плитці або «прибрати» в рядку — прибирає його.
- Мотогодини підставляються як «останнє відоме + прогноз наробітку», користувач править.
- Після збереження — снекбар «Записано» з кнопкою **Скасувати** (5 сек).
  Жодних діалогів підтвердження.
- **«Додати ще роботу»** — друга, менш помітна кнопка. Зберігає й одразу відкриває
  порожній аркуш із тією ж датою. Це відповідь на «gets a little tedious when you do
  multiple maintenance items in a single day».

#### ⚠️ Пакетний запис: дія має бути видимою всередині аркуша

Перша реалізація кнопки нічого не робила візуально — лише міняла заголовок
угорі аркуша, куди в цей момент ніхто не дивиться. Це той самий клас помилки,
що й плитки без заголовка: **дія без видимого наслідку читається як зламана кнопка.**

Як воно працює тепер:

1. Натиснули «Додати ще роботу» — поточна робота йде **в чергу**, а не в базу.
2. У тілі аркуша, під заголовком, зʼявляється смужка
   «**Уже записано, лишилось зберегти** · ✓ Імпелер забортної помпи».
   Кожна наступна робота додає рядок. Це і є видимий наслідок дотику.
3. Аркуш скидається й питає **який вузол**: поле з тим самим індексом пошуку,
   що й на екрані «Пошук» — «цинки», «racor», «мачта» тут теж працюють.
4. Щойно вузол обрано, аркуш **перебудовується під його тип**: обрали
   «Страховка» — рядки стають `ОНОВЛЕНО` / `ДІЄ ДО`, плитки міняються на
   `Скан поліса · Номер полісу · Вартість · Нотатка`, а сама кнопка «Додати ще
   роботу» **зникає**, бо документи не записують пачками.
5. «Зберегти» фіксує всю чергу однією дією. Снекбар рахує:
   «Записано 2 роботи», «Записано 5 робіт».

**Черга, а не послідовні збереження.** Поки не натиснуто «Зберегти», нічого не
записано, і смужка це прямо каже: «лишилось зберегти». Інакше «Скасувати» в
снекбарі мусило б відкочувати кілька записів, а це вже не скасування, а історія
транзакцій.

**Форм множини три, і без них не обійтися.** «Записано 2 роботи» / «5 робіт» /
«21 роботу» — в українській `one / few / many`, і 21 повертається до форми
однини. У прототипі це функція, в застосунку — `<plurals>` у `strings.xml`.
Англійське `2 jobs / 5 jobs` цієї проблеми не має, і саме тому її легко
проґавити, будуючи інтерфейс з англійської.

Дата підтримує неточність: «Сьогодні / Вчора / Обрати дату / **Не памʼятаю точно**»,
останнє пише `date_precision = MONTH|YEAR|SEASON`. Люди дозаповнюють журнал заднім числом.

## 5. Картка вузла — порядок блоків має значення

Порядок продиктований тим, **де людина стоїть**, коли відкриває цей екран.

```
1. Назва, виробник, модель, серійний
2. НАСТУПНЕ ТО         ← «через 3 мотогодини» / «~14 серпня»
3. ПАСПОРТ (spec_json) ← олія 15W40, 4.2 л · фільтр Volvo 3809721 · момент 45 Нм
4. [ + Запис ]         ← первинна кнопка
5. Фото за часом       ← горизонтальна стрічка, найновіше зліва
6. Історія робіт       ← згорнута до 5 останніх, «показати всі»
7. Запчастини на складі
8. Постійні нотатки
9. Регламент (інтервали) — рідко міняється, тому внизу
```

**Паспорт на 3-й позиції — свідомо.** Це відповідь на питання «яка олія і скільки»,
яке ставлять, стоячи в магазині. У конкурентів воно закопане в налаштуваннях вузла.

Фото за часом — прямо з форуму: «comparing photos over time is very helpful in
troubleshooting root cause of a problem». Один вузол, усі фото за 6 років, за датою.

## 5.1. Історія вузла складається з полів запису, а не з вільного тексту

Питання власника: *«Як формується саме така історія? З пункту „Нотатки“?»*
У прототипі стояли три рядки, вписані руками — і вони **суперечили аркушу,
який ми щойно збудували**. Аркуш збирає сім полів, історія показувала одне
речення й викидала решту.

Правильна відповідь: рядок історії **складається** з того, що збережено.

```
2025-06-12   Заміна                        512 год     ← дата · тип · лічильник
             Jabsco 17937-0001 · 1 240 ₴ · 1 знімок    ← деталь · вартість · фото
             Лопаті цілі, корпус без задирів            ← нотатка
    ──────── через 410 днів · 187 мотогодин ────────    ← рахується, не вводиться
2024-04-28   Заміна                        325 год
```

Нотатка — лише останній рядок. Усе інше приходить із плиток, які ми зробили
опційними: `ЛІЧИЛЬНИК`, `ДЕТАЛЬ`, `ВАРТІСТЬ`, `ФОТО`.

**Назви вузла в рядку немає навмисно.** Стояло «Заміна імпелера» всередині
сторінки «Імпелер забортної помпи» — те саме сказане двічі. На екрані шириною
380 px це коштує половину рядка.

### Проміжок між записами — головне число, і його не було

`410 днів · 187 мотогодин` не вводить ніхто: це різниця між сусідніми записами.
І саме воно відповідає на питання, заради якого журнал ведуть.

У каталозі регламент імпелера — **500 год / 1 рік**. У цього власника виходить
**187 год / 410 днів**. Тобто він міняє **за календарем, і щоразу з
запізненням на півтора місяця**. Жодне окреме поле цього не показує — видно
лише з відстані між рядками.

Це прямо живить клин №1: прогноз рахується з реальної історії, а не з
паспортного інтервалу.

## 5.2. Вичитка моряком: шість разів бракувало не назви, а послідовності

Окремий прохід «очима моряка» дав шість правок, і в усіх однакова природа:
пункт називав правильну дію, але не той порядок, у якому вона має статися.
**На човні порядок і є процедурою.**

| Пункт | Чого бракувало |
|---|---|
| Спуск на воду | Не «оглянути проходи», а **підняти пайоли ще в стропах** і дивитися кінгстони, штуцер лага й сальник вала — доки кран може підняти назад |
| Гальюн | Спершу **перекрити вхідний кінгстон**, тоді опустити шланг забору в антифриз. І він **рожевий** — колір на виході й є контролем |
| Аноди навесні | Не лише замінити, а **не допустити необростайки на них і на контактних поверхнях**. Пофарбований анод не працює, і за сезон струми зʼїдають гвинт |
| Імпелер восени | Не просто зняти, а **промити, змастити силіконом і покласти в пакет біля помпи**. Залишений у корпусі бере форму й лопається за десять хвилин навесні |
| Балони жилетів | **На кухонних вагах** проти вибитої повної маси — мікротріщина не спрацьовує на індикаторі |
| Аптечка | Дата **препарату, що спливає найпершим**, бо в аптечці їх десятки |

### Два вузли з річним регламентом, яких не було в жодному чеклісті

| Вузол | Чому саме вони губляться |
|---|---|
| **Аварійний румпель** | закисає під кришкою в ахтерпіку, і вперше його дістають тоді, коли керма вже немає |
| **Аварійні дерев'яні пробки** | лежать купою в рундуку замість того, щоб висіти **кожен на своєму кінгстоні** |

Обидва — та сама природа: спорядження, якого не торкаються від дня купівлі до
дня, коли воно знадобиться. Тепер перевірка безпеки — **30 пунктів**, і в ній
є пробне перекладання румпелем.

Знайшлися вони не механічною перевіркою: у каталозі обидва були, з розкладом
`days: 365`, просто на них ніхто не послався. Це та частина роботи, якої
валідатор не робить.

## 5.4. Заглушка навігації — той самий щит, лише на іншому місці

Після того, як сторінка вузла почала рендеритись із вибраного, зовнішня оцінка
сказала: «сліпих зон більше не залишилось». Перевірка це не підтвердила.

Навігація мала чотири вкладки на **три** екрани:

| Вкладка | Куди вела | Куди веде тепер |
|---|---|---|
| Зараз | `s-now` ✓ | `s-now` |
| Човен | `s-detail` — сторінка **одного вузла**, а не дерево човна | `s-boat` — дерево категорій (§8.5) |
| Журнал | `data-go="now"` — **та сама заглушка** | `s-log` — стрічка з проміжками (§8.8) |
| Склад | `data-go="now"` — **та сама заглушка** | `s-store` — локації, дефіцит, QR (§8.9) |

Жодної заглушки в нижній панелі більше немає. Десктопний селектор над рамкою
телефона теж веде на всі чотири екрани — раніше в ньому були лише
`Зараз · Пошук · Вузол`, тобто на ноуті до дерева й журналу доводилося
гортати сторінку до нижньої панелі самого телефона.

Дві з чотирьох вкладок були рівно тим `go("now")`, що приховав чотири дефекти.
І окремо: **113 пунктів чеклістів існували лише як JSON.** Усе, що ми про них
вирішили — три стани, розділення `logs`, фільтр за профілем, інфінітив проти
статива — жоден екран не показував.

### Тиха заглушка гірша за видиму

Вкладка, що безшумно повертає на «Зараз», читається як «нічого не сталося» —
і саме так пропущений екран лишається непоміченим. Тому «Журнал» тепер
відкриває екран, який **прямо каже, що його немає** і чому заглушка видима.

Це не косметика: єдина причина, чому роутинг вузла був зламаний місяцями
прототипу, — що збій виглядав як відсутність збою.

## 5.5. Екран чеклістів

```
( Консервація ) ( Розконсервація ) ( Перевірка безпеки ) ( Перед виходом )

1 / 34    6 не стосується цього човна · 1 пропущено

✓  Замінити оливу й фільтр до консервації, а не навесні
   Моторна олива   [запис]
○  Замінити оливу в редукторі
   Олива редуктора  [запис]
   не стосується / пропустити
–  Промити контур забортної води прісною
   пропущено: немає деталі, замовлено

1 позначка створить запис у журналі й скине інтервал вузла. Решта — ні.
```

Що стало видно тільки на екрані:

**Фільтр працює й це помітно.** На демо-човні (монокорпус, дизель, LPG, зимує
на суші) із 40 пунктів консервації показано **34**, і в заголовку прямо
написано «6 не стосується цього човна» — не приховано, а порахувано.

**Розділення `logs` читається з першого погляду.** Мітка `[запис]` на 7 з 34
у консервації, `[запис + дата]` на 9 з 30 у перевірці безпеки, і **нуль міток
у «Перед виходом»** — саме те рішення, що чекліст перед виходом не має
засмічувати журнал.

**Пропуск не буває безшумним.** Поруч із пропущеним пунктом стоїть причина.
Це відрізняє його від відкладення: пропуск стосується лише цього проходження
списку, відкладення переносить сам термін вузла.

### Дієслово теж має відмінюватись

`1 позначка **створять**` — помилка, яку англійська не змушує помітити.
Українською змінюється не лише іменник:

| | |
|---|---|
| 1 | позначка **створить** запис і **скине** інтервал |
| 2 · 4 | позначки **створять** запис і **скинуть** інтервал |
| 5 · 11 | позначок **створять** … |
| 21 | позначка **створить** … |

Три форми потрібні **кожному** слову в реченні, що узгоджується з числом, а не
лише тому, що стоїть біля цифри. У `strings.xml` це означає, що `<plurals>`
мусить охоплювати весь фрагмент, а не одне слово.

## 6. Решта екранів, стисло

**Човен.** Список 21 категорії з лічильником вузлів і кольоровою крапкою стану.
Категорії, що не підходять профілю судна, — під згорткою «Показати все» внизу,
не видалені. Тап → вузли категорії. Глибина максимум 3 рівні.

**Журнал.** Зворотна хронологія, згруповано по роках і місяцях. Закріплене поле пошуку.
Чипи фільтрів: категорія · тип роботи · рік. Кожен рядок — дата, вузол, опис, мініатюра фото.

**Пошук.** Окремий повноекранний. Один рядок, результати згруповані:
Записи · Вузли · Запчастини · Документи · Фото (за підписом і OCR чеків).
Знайдене слово підсвічено. Порожній стан показує останні запити, не порожнечу.

Підказки з другого символу, ранжування, синоніми й крос-мовний пошук —
**[search-spec.md](search-spec.md)**. Ключове правило звідти: **показуємо одну
назву, шукаємо за багатьма**. Синоніми ніколи не відображаються.

**Склад.** Групування за локацією (ящик/відсік). Велика кнопка **сканувати QR** угорі.
Тап по локації → вміст. Кнопка «Друк наліпок» → PDF-аркуш.

**Чеклісти.** Список вбудованих і власних. Запуск → повноекранний список із великими
чекбоксами, прогресом угорі, кнопкою «Пропустити» біля кожного пункту.
Завершення створює записи з тегом (напр. `консервація`) для відмічених пунктів,
що мають вузол.

**Дані.** Кнопка «Експортувати все зараз», вибір папки для автобекапу (SAF),
імпорт, і чесний текст: що саме лежить у папці й що буде читатись, якщо застосунок зникне.

**Онбординг — рівно 3 екрани.** (1) «Маю таблицю» / «Почати з нуля».
(2) Профіль судна — картки з іконками, не випадайки. (3) «Готово. Створено 47
позицій обслуговування» → одразу «Зараз». Порожнього екрана не існує в жодному
сценарії.

### ⚠️ Перше питання — вітрильне чи моторне, і воно керує рештою

Спершу профіль був «6 питань» одним рівним списком. Це помилка: **питання не
рівноцінні.** Тип корпусу коштує один дотик, на нього не помиляється ніхто, і
він одразу знімає чотири категорії й понад 50 вузлів.

| | Вітрильне | Моторне |
|---|---|---|
| Вузлів у каталозі | **247** | **196** |
| Категорій | 16 | 13 |
| Чого немає | причепа | стоячого такелажу, рангоуту, вітрил, газу |

Тому корпус іде **першим**, а решта питань залежать від відповіді:

```
1. Корпус ── вітрильне ─→ 2. Рушій   (сейлдрайв · вал · підвісний · електро · немає)
        │                 3. Тип рангоуту   ← лише тут
        │                 4. Кіль           ← лише тут
        │                 5. Охолодження    ← лише якщо стаціонар
        │                 6. Зимівля
        │                 7. Обладнання     (з закруткою в списку)
        │
        └── моторне ───→ 2. Рушій   (стаціонар · сталовий привід · підвісний · вал · електро)
                          3. Охолодження    ← лише якщо стаціонар
                          4. Зимівля
                          5. Обладнання     (без закрутки, з причепом)
```

**Вітрильнику — 7 питань, моторному — 5.** І списки варіантів теж коротшають:
у моторного немає сейлдрайва, у вітрильника — сталового привода.

Питання «Охолодження» (забортна вода / кільове) взагалі не має сенсу для
підвісного, тому воно залежить не від корпусу, а від рушія. Це той самий
принцип: **не питати того, що вже випливає з попередньої відповіді.**

Технічно нічого нового не потрібно: правила застосовності вже стоять
на категоріях і вузлах у `catalog.json` (`hullAny`, `propulsionAny`,
`extrasAny`…). Онбординг просто **читає той самий словник**, у якому порядок
питань — це порядок від найдешевшого й найвирішальнішого до найдрібнішого.

## 7. Функції, які реально корисні власнику

Відсортовано за співвідношенням «користь / вартість розробки». Кожна привʼязана до доказу.

1. **«Зроблено» просто зі сповіщення.** Без відкриття застосунку.
   Найбільший важіль проти забування. Не заявляє ніхто.
2. **Паспорт вузла за 2 дотики.** «Яка олія, скільки літрів, який номер фільтра» —
   найчастіше питання поза човном. У форумних таблицях це окрема вкладка `parts`.
3. **Прогноз дати настання.** Єдина функція, яку таблиця не дає принципово:
   «Not very good for predictive maintenance». Рахується з ряду показників лічильника.
4. **Список покупок перед виїздом.** ⭐ Автоматично: усе, що настає найближчі 30 днів,
   мінус те, що вже є на складі = список із номерами деталей, готовий до магазину.
   Дешево реалізувати, немає ні в кого, і потрапляє точно в момент, коли людина
   вже їде по запчастини.
5. **Фото лічильника → цифра.** ML Kit, офлайн. Сканування чеків є в кількох,
   лічильника — ні в кого.
6. **Галерея вузла за часом.** Діагностика по фото, пряма цитата з форуму.
7. **Пошук по всьому**, включно з текстом розпізнаних чеків.
8. **QR-наліпки на ящики.** Власники вже тримають нумеровані ящики й шукають вміст у таблиці.
9. **Кілька записів за один візит** без повторного проходу форми.
10. **Режим механіка.** Тимчасове посилання/пакет, у якому механік може дописати свою
    роботу й фото, не бачачи решти. Запит №2 за частотою на форумах.
11. **Терміни документів і безпеки в тому ж списку «Зараз».** Реєстрація EPIRB,
    страховка, фальшфейєри, сервіс плота. У форумних таблицях це окрема вкладка
    «administration reminders», а в застосунках зазвичай або немає, або окремо й забуто.

Свідомо **не** робимо в v1: навігацію, погоду, AIS, соцфункції, чат, AI-асистента.

## 8. Правила взаємодії

- **Жодної дії лише свайпом або лише довгим натисканням.** Завжди має бути видима кнопка.
  Мокрі руки й рукавички свайп не переживають.
- **Скасування замість підтвердження.** Снекбар «Скасувати» замість діалогу «Ви впевнені?».
  Виняток — видалення вузла з історією (він архівується, а не видаляється).
- **Ніколи не показувати помилку мережі.** Її не існує: усе локально.
  Бекап у папку робиться тихо у фоні, статус видно лише на екрані «Дані».
- **Числа крупно, підписи дрібно.** «247 / 250 мотогодин» — число головне.
- **Колір ніколи не єдиний носій сенсу.** Червона крапка завжди супроводжується текстом
  («прострочено»), бо сонце вбиває кольори, а частина аудиторії — чоловіки за 50
  зі зниженим кольоросприйняттям.
- **Порожні стани містять дію**, не картинку. «Ще немає записів → Додати перший».

## 8.1. Палітра: скільки місця займає #14403A

Тон затверджений, але на прототипі екран читався важко, і причина була не в
тоні, а в **площі**. Кнопка «Зроблено» на кожній картці — суцільна заливка
#14403A на всю ширину, 46 px висоти. Шість карток — шість темних смуг, і фірмовий
колір із акценту перетворювався на тло.

**Три правила, які це лікують.**

**Одна залита кнопка на екран.** На картці кнопка тепер *тональна*: фон
`--container` #C2DAD4, текст #14403A. Це все ще кнопка й усе ще зелена, але вона
не забиває картку. Залита лишається одна на екран — «Зберегти» в аркуші запису,
де вона справді єдина головна дія.

Логіка тут не косметична: **стан картки вже сказаний рядком «чому»** — червона
плашка «прострочено 12 днів», бурштинова «за 8 мотогодин». Кнопка, яка повторює
ту саму терміновість заливкою, дублює інформацію й водночас глушить її.

**Тональна кнопка має власний передній план.** Токен `--on-container`, а не
`--primary`: у темній схемі #6BA599 на #1E5449 дає лише **3.1:1** і провалює AA
для тексту кнопки. Замінено на #9CD0C3 — **5.05:1**. У світлій 7.8:1, у «Сонці» 9.9:1.

**Зелений більше не означає «Відкладено».** Раніше `--deferred` дорівнював
`--primary` — той самий #14403A позначав і бренд, і статус. Виходила нісенітниця:
здоровий вузол сірий, а відкладений — фірмово-зелений. Тепер відкладене має свій
шиферно-синій (#3D5A6C / #9EC2D6 / #22404F), який не сперечається ні з червоним,
ні з бурштиновим, і зелений лишається лише кольором дії.

| Роль | Світла | Темна | Сонце |
|---|---|---|---|
| Дія (заливка) | #14403A | #6BA599 | #0E2E29 |
| Дія (тональна) | #C2DAD4 / #14403A | #1E5449 / #9CD0C3 | #C2DAD4 / #0E2E29 |
| Прострочено | #B3261E | #FF8A7E | #8C1D18 |
| Скоро | #8A5200 | #FFB95C | #6B4000 |
| Відкладено | #3D5A6C | #9EC2D6 | #22404F |
| Норма | #4A5F5B | #9BB0AB | #243B36 |

Правило з п.8 лишається чинним: **колір ніколи не єдиний носій сенсу.** У кожної
картки є ще й гліф (● ◐ ○ ◇) і текст.

## 8.1.1. Три польові дрібниці, які коштують більше, ніж виглядають

### Кроки замість клавіатури — і чому вони не вміщаються в один рядок

У рукавичках два дотики по `+10` і три по `+1` швидші, ніж викликати м'яку
клавіатуру, яка закриває пів екрана. Кнопка **56 px**, а не мінімальні 48 dp за
Material: на хитавиці цільова зона мусить пережити не лише неточний дотик, а й
те, що човен рухається під пальцем.

**⚠️ Перша версія ставила кнопки в один рядок зі значенням — і зламала поле.**
Заміряно: контейнер 268 px, чотири кнопки плюс підпис одиниці забирають 244, а
полю лишається **19 px**. У ці 19 браузер домалював власні спінери `type=number`
— і цифра зникла за стрілками.

56 px тут не те, від чого варто відмовлятись. Відмовитись треба від припущення,
що кроковий лічильник належить тому самому рядку, що й число: **ряд кнопок під
палець хоче ширини**, а на екрані 380 px її не лишається після колонки підпису
й кнопки «прибрати».

```
ЛІЧИЛЬНИК   ┌──────────────────────────┐   ✕
            │ 512                 год  │
            └──────────────────────────┘
            ┌──────┐┌──────┐┌─────┐┌──────┐
            │ −10  ││  −1  ││ +1  ││ +10  │   ← 71×56 кожна
            └──────┘└──────┘└─────┘└──────┘
            Скільки годин на лічильнику зараз.
```

Після правки: поле **223 px**, кнопки **71×56**, нуль переповнення. Нативні
спінери прибрані назовсім — вони дублюють ряд, непридатні в рукавичках і саме
вони з'їли цифри.

Розмітка ряду **одна** (`STEPROW`) для обох місць, де крокують число: поле
лічильника й дзеркалення бортів. Дві копії — це те, як вони розходяться.

### Відступ від жестової смужки Android

Первинна кнопка на всю ширину внизу аркуша стояла впритул до системної смужки
жестів. Мокрий великий палець, який тягнеться до неї, дає системі
**swipe-up-to-home** — і застосунок згортається посеред введення.

Тепер `padding-bottom: calc(22px + env(safe-area-inset-bottom))` для аркуша й
`calc(10px + inset)` для нижньої навігації. Самого `env()` недостатньо: він
описує фізичну недосяжну зону, а не зону, де жест перехоплює дотик.

### ⚠️ Дзеркалення бортів — і чому лічильник не копіюється

На здвоєній установці оливу, фільтри й імпелери міняють на обох двигунах за
один захід. Тому після збереження на першому аркуш пропонує другий.

Але **лічильники двох двигунів не збігаються** — за сезон маневрувань різниця
набігає 5–30 годин. А швидкість зносу рахується **на кожен лічильник окремо**
(`Meter` привʼязаний до `Component`, не до судна — [product-spec.md](product-spec.md), п.3).

> Скопіювати показник першого двигуна на другий означало б **тихо зіпсувати
> саму історію, на якій тримається прогноз.** Зручність, що псує дані, гірша
> за відсутність зручності.

Тому крок дзеркалення **питає** показник другого борту, підставляючи те, що
**цей** двигун показував останнього разу:

```
┌────────────────────────────────────────────┐
│ Записано на лівий борт                     │
│ На здвоєній установці це роблять на обох.  │
│ Лічильники не збігаються, тому введіть     │
│ показник правого борту окремо.             │
│                                            │
│ ПРАВИЙ БОРТ  −10 −1 [ 498 ] год +1 +10     │  ← 498, а не 522 з лівого
│                                            │
│  ┌──────────────────────────────────────┐  │
│  │   Записати й на правий борт          │  │
│  └──────────────────────────────────────┘  │
│  ┌──────────────────────────────────────┐  │
│  │   Тільки лівий                       │  │
│  └──────────────────────────────────────┘  │
└────────────────────────────────────────────┘
```

Крок зʼявляється **лише** для вузлів, які каталог позначає `perEngine`, і лише
на судні з двома двигунами. На корпусних анодах його немає — там дзеркалити
нічого.

Снекбар розрізняє шляхи: «Записано на два двигуни · правий 502 год» проти
звичайного «Записано».

**Баг, знайдений під час перевірки.** Перша версія міняла `id` кнопки перед її
текстом, тож наступний запрос повертав `null`, виняток обривав обробник — і
аркуш лишався переписаним наполовину: панель дзеркалення видно, а кнопки
з попередніми підписами. Виняток у делегованому обробнику **нічого не пише в
консоль користувачеві**, тому в застосунку це виглядало б як «кнопка іноді не
працює». Виправлено: вузли беруться у змінні, текст ставиться до `id`.

## 8.1.2. Моноширинний — там, де вирівнюються цифри, і більше ніде

У чеклісті назви вузлів читалися як дірки в рядку: «Моторна   олива»,
«Фільтр-сепаратор   палива». Ні подвійних пробілів, ні `word-spacing` там не
було — рядок стояв **моноширинним шрифтом**, а в IBM Plex Mono пробіл шириною
літери. В англійському `Part number` це майже не видно; у багатослівній
українській назві — видно одразу.

> **Моно там, де цифри вирівнюються в колонку. Sans там, де цифр немає.**

| Місце | Шрифт | Чому |
|---|---|---|
| «прострочено 12 днів · 512 з 500 мотогодин» | **моно** | числа вирівнюються по картках — це й є причина платити за моноширинний |
| «через 410 днів · 187 мотогодин» | моно | те саме |
| `Jabsco 17937-0001 · 1 240 ₴` | моно | артикул і сума скануються оком |
| Дати в історії | моно | `tabular-nums` тримає колонку |
| **«Моторна олива [запис]»** | **sans** | **жодної цифри — лише дірки від пробілів** |

Правило дрібне, але воно вирішує, і його легко порушити: моно виглядає
«технічно», і спокуса вдягнути в нього все службове велика. Ознака помилки
проста — **якщо в рядку немає цифр, моно там не за що не відповідає.**

## 8.2. Червоний нічний режим — четверта схема, і не косметична

Дослідження ринку принесло один пункт, якого в нас не було зовсім, і він
серйозний.

**Адаптація ока до темряви триває до 30 хвилин**, і один погляд на екран із
білим або синім спектром руйнує родопсин у паличках сітківки. Стерновий на
пів години втрачає здатність розрізняти навігаційні вогні. **Звичайна темна
тема Android тут не допомагає** — вона лишає білий текст, просто на темному
тлі.

Тому схем тепер чотири: `Світла · Темна · Сонце · **Ніч**`.

### Наслідок, який виявився структурним, а не декоративним

Червона монохромна палітра **не має чим розрізняти стани**. `OVERDUE`,
`DUE_SOON` і `OK` не можуть відрізнятися відтінком, бо відтінок один.
Лишається яскравість — а її діапазон вузький, бо всю схему тримаємо тьмяною
навмисно.

Спроба підняти всі рівні до AA дала колізію: приглушений текст мусив стати
**яскравішим за статус «скоро»**. Тобто на трьох рівнях яскравості не
вміщаються і текстова ієрархія, і статусна.

Рішення — свідомо сплющити палітру:

> **У нічному режимі яскравість витрачається лише на статус. Ієрархія тексту
> переходить на вагу й розмір.**

| Роль | Колір | Контраст |
|---|---|---|
| Прострочено | `#FF7A55` | 6,91:1 — **єдине, на що витрачається яскравість** |
| Скоро · основний текст | `#E8543A` | 5,12–5,62:1 |
| Норма · приглушений · відкладено | `#D14A32` | 4,52:1 |
| Тло · картка | `#080302` · `#0F0604` | — |

Це працює лише завдяки правилу з п.8: **колір ніколи не єдиний носій сенсу.**
Гліфи ● ◐ ○ ◇ уже стояли на картках, і саме вони тепер несуть стан, коли
відтінок цього робити не може. Правило, ухвалене з думкою про сонце й про
чоловіків за 50 зі зниженим кольоросприйняттям, окупилось у зовсім іншому
місці.

### AA і тьмяність не конфліктують — це виміряно

Головне заперечення проти AA в нічному режимі — що яскравий текст зруйнує
адаптацію. Числа кажуть інше:

| | Яскравість (L) |
|---|---|
| Темна схема, основний текст `#E4EDEA` | **0,83** |
| Темна схема, приглушений `#9BB0AB` | **0,41** |
| **Ніч, найяскравіший елемент** `#FF7A55` | **0,36** |

Найяскравіше, що є в нічній схемі, **тьмяніше за приглушений текст темної**.
Тобто пройти AA тут не коштує світла — усі десять пар перевірено, провалів
нема.

## 8.3. Два поля профілю, яких бракувало

**`water` — моя ж помилка.** Вимір `salt · brackish · fresh` було додано до
`profileVocabulary` і в `specHints` анодів, але **не до сутності `Vessel`**.
Тобто паспорт анода питав те, на що судно не могло відповісти. Виправлено.

**`hin` / `make` / `model`.** Номер корпусу (HIN у США, CIN в ЄС) вибитий на
транці з правого борту й наполовину нечитний — саме тому він має лежати в
полі, яке шукається: його питають страховик, сюрвеєр і магазин запчастин, і
його першим перевіряє покупець.

## 8.3.1. Кілька суден: один потік із підписом, а не режим

Пропозиція власника була зробити стартовою сторінкою список суден. Відповідь —
**ні як стартову, але так як екран**, і причина не в естетиці.

### Чому не хвіртка

Фліт-екран на старті **коштує дотик кожному при кожному запуску, щоб
обслужити меншість**. У більшості власників один човен, і екран з однією
карткою — це двері, за якими нічого немає.

Гірше: він суперечить головному. Ми відкриваємось тим, що горить, а найсильніший
важіль — «Зроблено» **зі сповіщення, не відкриваючи застосунок** (п.7). Шлагбаум
перед цим — крок у бік систем управління флотом, від яких ми відрізняємось.

### Чому й не «поточне судно»

Перша реалізація перемикача була **режимом**: обрав судно — усе стало його.
Це класична помилка режиму, і тут вона дорога: ви в «Тузику» й записуєте
заміну оливи яхти, бо ніщо на картці з вами не спорить. А зіпсована історія
лічильника — це саме те, з чого рахується прогноз.

### Що працює: один потік, судно на картці

```
( ⛵ Вихід у море — перевірка, 6 пунктів )
[ Усі (7) ]  [ Оріон (5) ]  [ Тузик (2) ]
3 прострочено   4 скоро

● Імпелер забортної помпи            · Оріон
● Корпусні аноди                     · Оріон
● Клапани і шви балонів              · Тузик
◐ Оливний фільтр                     · Оріон
◐ Олива редуктора підвісного         · Тузик
```

**Режиму немає — немає й помилки режиму.** Кожна картка несе своє судно, тому
записати на не той двигун неможливо.

**Чипи — фільтр, а не стан.** За замовчуванням «Усі». Один дотик, щоб
зосередитись, і нічого, що можна забути ввімкненим.

**Власник одного човна цієї механіки не бачить взагалі.** Ряд чипів
прихований, підпису судна на картках немає — перевірено: `#vfilter.hidden`
і нуль `.vessel-tag`. Він не платить за мультисудновість жодним пікселем.

**Сортування спільне**, за станом: прострочене йде поперед скоро незалежно від
судна. Тузик із простроченими балонами стоїть вище за яхту зі «скоро», бо
терміновість не належить корпусу.

### Фліт-екран — паспортний стіл

Відкривається з назви в шапці. Там повний паспорт кожного борту, зведені
лічильники й додавання:

```
Оріон · Bavaria 36                    2 ● 3 ◐
  Профіль      монокорпус · дизель · шлюп · фін-кіль
  Акваторія    солона
  Зберігання   зимує на суші
  HIN / CIN    UA-BAV36A1B203
  [ Редагувати ]  [ Експорт ]

Тузик · Highfield 310                 1 ● 1 ◐
  Профіль      RIB · підвісний · без рангоуту
  ...
  [ Дивитися це ]  [ Експорт ]

+ Додати судно
```

«Дивитися це» ставить фільтр на це судно й повертає на «Зараз» — тобто робить
те саме, що чип, лише з місця, де ви щойно читали паспорт.

**Кількості вузлів на картці немає навмисно.** Копія каталогу в прототипі не
несе правил `appliesTo`, тому порахувати їх чесно неможливо — а число, яке ми
не можемо порахувати, гірше за його відсутність.

## 8.4. Налаштування — і як додати друге судно

Питання власника: *«Які параметри ми можемо туди внести? Як додавати
плавзасоби?»* Екрана не було спроєктовано взагалі — навіть у списку пʼяти
невиконаних він не значився.

**Налаштування живуть у меню верхньої панелі, не у вкладці.** Вкладок чотири,
і всі чотири — робочі місця. Налаштування відкривають раз на сезон.

Шапка має рівно три елементи, і кожен відповідає на своє питання:

```
┌──────────────────────────────────────────────────┐
│ Оріон · Bavaria 36 ▾            ⋮        🔍      │
└──────────────────────────────────────────────────┘
   ↑ судно й парк           ↑ налаштування   ↑ пошук
```

**Назва судна — це кнопка.** Тап відкриває парк і «+ Додати судно». Це єдине
місце, де судно перемикається: воно не займає вкладки й не з'їдає рядок на
«Зараз», бо власників двох човнів мало, а екран у всіх один.

**`⋮` — усе, що відкривають раз на сезон:** мова, судно, профіль, акваторія,
сезон, одиниці, сповіщення, дані — і три сезонні чеклісти. «Перед виходом»
у меню **немає**: він на чипі (п.2), бо працює щотижня.

**Мова — окремий рядок від одиниць**, першим у списку. Це не косметика: саме
злиття цих двох понять і було дефектом, який ми виправляли в
[i18n-uk.md](i18n-uk.md) п.8.1 — інтерфейс українською не означає літри.

### Що туди йде — і нічого зверх того

| Розділ | Параметри | Чому саме тут |
|---|---|---|
| **Судно** | назва · HIN/CIN · виробник · модель · рік · довжина · фото | HIN питають страховик, сюрвеєр і магазин; напам'ять його не знає ніхто (п.8.3) |
| **Профіль** | корпус · рушій · охолодження · рангоут · кіль · к-ть двигунів · обладнання | ті самі 5–7 питань онбордингу; правка **перебудовує дерево вузлів** |
| **Акваторія** | солона · солонувата · прісна | єдине, що вирішує **матеріал анода**, а не смак (п.8.2) |
| **Сезон** | місяць спуску · місяць підйому | вимикає накопичення мотогодин на зимівлю ([product-spec.md](product-spec.md), п.5.5) |
| **Одиниці** | пресет + перевизначення на величину | галон — не одна одиниця; зберігаємо SI, конвертуємо на показ ([i18n-uk.md](i18n-uk.md), п.8.1) |
| **Сповіщення** | година доби · які стани будять · вікна попередження | Dirona дає 50 год на головний двигун і 15 на допоміжний — вікно **на регламент**, не одне на застосунок |
| **Дані** | папка бекапу (SAF) · «Експортувати зараз» · імпорт · PDF-паспорт | єдиний екран, де взагалі згадується файлова система |
| **Мова** | українська · English | окремо від одиниць. Це і був дефект п.8.1 |

**Схеми тут немає.** Перемикач `Світла · Темна · Сонце · Ніч` стоїть **у шапці
головного екрана**: його вмикають на палубі опівдні або на нічному переході,
тобто саме тоді, коли лізти в налаштування неможливо (п.8.2).

### Друге судно — це онбординг, а не форма

Модель тримає кілька суден із першого дня: `Vessel` — окрема сутність, усе
решта прив'язане до неї ([product-spec.md](product-spec.md), п.6.1). Бракує
лише двох речей в інтерфейсі:

```
Шапка: Оріон ▾            ← тап по назві судна
       ├─ Оріон · Bavaria 36      ✓
       ├─ Тузик · Zodiac 3.1
       ├─ ──────────────
       └─ + Додати судно          → той самий онбординг, 3 екрани
```

**«Додати судно» повторно запускає онбординг.** Окремої форми немає навмисно:
онбординг уже питає рівно те, що потрібно, і вже фільтрує питання за типом
корпусу. Друга форма поруч розійшлася б із ним за перший же новий параметр —
рівно як `water` розійшовся зі словником.

Типовий випадок — не два човни, а **«яхта + тендер»**: підвісний мотор на
тузику має власні мотогодини, власну оливу в нозі й власні аноди. Це друге
судно, а не вузол першого, бо в нього свій профіль і свій лічильник.

Перемикання судна **не** живе у вкладці й **не** займає місця на «Зараз»:
власників двох човнів мало, а екран у всіх один.

## 8.5. «Човен» — дерево вузлів, і чому категорія мусить заслужити свій рядок

Екран «Човен» відповідає на питання, яке не має місця на «Зараз»: **що взагалі
є на цьому судні**. «Зараз» показує те, що вимагає уваги — тобто десяток
позицій зі ста. Решта існує, але ніде не видна.

Структура: шапка з профілем і підсумком → згорнуті категорії → вузли всередині
→ під ними згортка «Не стосується цього судна».

### Підсумок у шапці має два незалежні числа

«253 вузли у 16 категоріях» — це два числа, які змінюються окремо. Android
`<plurals>` бере **одне**. Тому це два ресурси, `boat_nodes` і
`boat_categories_in`, а не один рядок із двома `%d`. Локатив («у 16
**категоріях**») — окрема форма від називного («16 **категорій**» у згортці
внизу), тож і окремий ресурс. Три ресурси на одну шапку — не надмірність, а
ціна того, що українська узгоджує відмінок.

### Категорія заслуговує рядок, якщо в ній є вузол на цьому судні

Перша версія рахувала живі категорії так: `fits(cat.appliesTo)`. Це давало
порожні рядки — категорія, чиє власне правило проходить, але всі вузли в ній
відсіяні. На 3-метровому тузику так залишився рядок «Камбуз та інтер'єр 0»,
бо камбуз не має власного правила, а плита й пральна машина відсіялися по
`cabin`.

Перший раз я «виправив» це, **видаливши** порожню категорію `other` з
каталогу. Це прибрало симптом і залишило правило. Правильне правило:

```js
const has = (c) => fits(c.r) && nodesOf(c.c).length > 0;
```

Тест `reference_vessels.py` рахує категорії так само, і саме розбіжність між
ними (9 у тесті проти 10 в прототипі) знайшла помилку.

### Причина в згортці збирається з вузлів, коли її немає в категорії

Категорія, яка спорожніла через свої вузли, не має власної причини — її
правило ж пройшло. Тому `whyNotCat()` спершу питає категорію, а якщо та
мовчить, збирає різні причини її вузлів:

> Камбуз та інтер'єр — цього обладнання немає в профілі · потрібен інший тип
> корпусу

### Кнопка «назад» називає екран, з якого прийшли

Сторінка вузла казала «← Зараз» незалежно від того, звідки її відкрили: з
дерева вона обіцяла повернення на екран, на якому користувач не був. Назва
береться з `aria-label` цільової секції, а не з окремої таблиці назв екранів —
друга таблиця назв це друга річ, яку забудеш оновити.

## 8.6. Назва вузла на картці «Зараз» — це вхід у вузол

Картка вміла «Зроблено» і «Відкласти», але сама назва була мертвим текстом.
Тобто на головному екрані можна було закрити роботу й відкласти її, і не можна
було спитати **що це таке** — перше питання нового власника.

Тепер назва з групою — одна кнопка `[data-open]` з шевроном, яка веде на
сторінку вузла.

### Картка називає вузол кодом, не текстом

Демо-рядки `DUE_ORION` / `DUE_TENDER` носили українські назви власного
написання. Три з десяти вже розійшлися з глосарієм:

| картка казала | каталог казав |
| --- | --- |
| Тендер і підвісний | Дінгі та підвісний мотор |
| Страховка | Суднове страхування |
| Клапани і шви балонів | Клапани і робочий тиск дінгі |
| Кільовий шов | Кільовий шов (стик кіля з корпусом) |

Це той самий дрейф, що поселив «джекштоки» в чеклістах, коли каталог уже
казав «Страхувальні лінійні леєри». Рядок тепер носить `c: "tender_valves"`, а
`n` і `g` підставляються з каталогу при завантаженні. Код, який не знайшовся,
показується на картці як `⚠ tender_valves`, а не кидає виняток: виняток на
завантаженні гасить усе — так одного разу мовчки помер пошук.

## 8.7. Арифметика на екрані мусить сходитися

Дерево показувало «253 вузли у 16 категоріях», під ним «Не стосується цього
судна — 4 категорії, 32 вузли», а в каталозі 323. Власник, який додасть два
числа, отримає 285 і не знайде решти **38**.

Ті 38 — вузли, відсіяні **всередині категорій, які на судні є**: олива
сейлдрайва в човні з валом, свічки запалювання в дизелі, кільове охолодження,
підйомний кіль. Вони не в активному списку й не в згортці. На тузику
ховалося не 38, а **225**.

Двічі мішалися й одиниці: `liveNodes` рахує **екземпляри** (два імпелери на
двомоторному), а 323 рахує **вузли**. На одномоторному човні це те саме
число, тому розбіжність не було видно.

### Що на екрані тепер

Згортка розділена за причиною, бо «у вас вал, тому сейлдрайв прихований» —
це корисна половина, і саме її викидали:

```
▾ Не стосується цього судна — 70 вузлів
    4 КАТЕГОРІЇ НЕ СТОСУЮТЬСЯ — 32 ВУЗЛИ
      Генератор — цього обладнання немає в профілі
      …
    38 ВУЗЛІВ У КАТЕГОРІЯХ, ЯКІ НА СУДНІ Є
      Корпус і підводна частина
        Підйомний кіль / шверт — потрібен інший кіль
        Транцеві плити та гідравліка — потрібен інший тип корпусу
      …
    ─────────────────────────────
    253 + 70 = 323 вузли каталогу
```

Останній рядок — моноширинний, за правилом §8.1.2: там вирівнюються цифри.

І інваріант у коді, а не лише в шапці:

```js
if (liveNodeCount + deadNodes !== totalNodes) {
  console.error("boat tree does not add up:", …);
}
```

Якщо колись спрацює — одна з трьох цифр бреше власникові.

### Чому «категорій, вузлів» у кнопці стало просто «вузлів»

Кнопка казала «4 категорії, 32 вузли». Коли до згортки додалися 38 вузлів із
живих категорій, «4 категорії» і «70 вузлів» перестали відповідати одне
одному: ті 70 лежать не в чотирьох категоріях. Одне число в одній одиниці —
вузли — його можна додати до шапки. Розбиття живе всередині.

## 8.8. «Журнал» — стрічка, і чому проміжок важливіший за сам запис

Шлях запису існував із самого початку: аркуш «Зроблено» пише `ServiceRecord`.
Шляху читання не було — жоден екран цього не показував, а блок «Історія» на
сторінці вузла був хардкодом на один компонент.

Структура: підсумок → фільтри → роки → місяці → записи, між якими **проміжок**.

### Проміжок належить між записами, а не всередині запису

«через 410 днів і 173 мотогодини після попереднього» — це не властивість
запису, це відношення двох. Тому окремий рядок між карточками, з відступом
під колонку дат.

Проміжок рахується до попереднього обслуговування **цього вузла на цьому
судні**, не до попереднього рядка в списку. Інакше після спільного «Зроблено»
на три вузли одного дня журнал казав би «через 0 днів».

І два числа знову незалежні: у застосунку це `log_gap_days` і
`log_gap_hours`, ніколи один рядок із двома `%d`.

### Точність дати мусить дожити до екрана

`ServiceRecord.precision` існує тому, що імпорт з Excel часто знає лише
місяць. Написати «12 серпня» для рядка, де в клітинці стояло «08.2023», —
це вигадати дані, і власник, який щойно імпортував таблицю, це помітить
першим.

* `DAY` — у колонці дат стоїть число, місяць дає заголовок групи;
* `MONTH` і `YEAR` — у колонці **тире**, а причина словами йде в рядок
  походження: «відомий лише місяць · з імпорту · аркуш "Двигун", рядок 42»;
* `YEAR` додатково **не отримує заголовка місяця**, якого не може
  підтвердити;
* неточний кінець робить неточним увесь інтервал: «**≈** через 271 день».

#### ⚠️ Чому не слово в колонці

Перша версія клала в колонку слова «місяць» і «рік». Колонка — **40px**, під
одну-дві цифри, і слово в неї не влазило: воно друкувалося **поверх назви
вузла** — «місяцьІмпелер забортної помпи».

Причина глибша за ширину. Колонка існує, **щоб цифри вирівнювалися по
вертикалі** — це те саме правило «моноширинний там, де вирівнюються цифри»
(§8.1.2). Слово в ній ламає рівно те, заради чого вона є. Рядок без відомого
дня має **видимо не мати дня**, і тире каже це одним знаком; місяць і рік уже
написані в заголовках груп над ним.

Колонка тепер має `overflow: hidden`, щоб наступний підпис не зміг тихо
надрукуватися поверх сусіда.

Жодна з 15 перевірок цього не бачила: усі вони читають текст і структуру, а
це була **геометрія**. Знайшлося з першого погляду на екран.

### Походження рядка

Запис, якого власник не вводив, каже про це — і каже **звідки**, щоб хибну
цифру можна було довести до клітинки:

> з імпорту · аркуш «Двигун», рядок 42

### Відмінки місяців — два списки, не один

«Червень 2026» у заголовку (називний) і «12 червня» в рядку (родовий).
Українська не дає одному списку служити обом, а не той відмінок читається як
машинний переклад. Тому `MONTH_NOM` і `MONTH_GEN` окремо.

### Колір лише там, де він змінює зміст

Мітки `WorkType` — сірі чипи, крім трьох: `REPAIR` червоний (ремонт це не
планове), `HAUL_OUT` і `LAUNCH` жовті (вони прив'язують сезон). Розфарбувати
всі десять означало б не сказати нічого.

### Порожній стан учить, звідки беруться записи

> Тут ще нічого немає. Кожне «Зроблено» на «Зараз» пише сюди запис — з датою,
> мотогодинами й фото.

Фільтр судна на порожньому журналі приховано: три чипи по «(0)» — це шум на
екрані, вся робота якого сказати «поки нічого».

### Фільтр категорій пропонує лише те, що може дати результат

Чипи будуються з категорій, у яких **справді є записи для вибраного судна**.
Фільтр із 20 варіантами, де 8 можуть дати результат, — це фільтр, що бреше.
Тому при переході на «Тузик» список чипів звужується до двох.

### Один набір записів, не два

Сторінка вузла тепер фільтрує той самий `LOG`. Свій масив `HIST` на один
компонент — це другий примірник набору даних, а два примірники це те, з чого
журнал і сторінка вузла починають розходитись у тому, коли міняли імпелер.

## 8.9. «Склад» — і ребро, якого не було в схемі

`StorageLocation` мала `qrCode` («Printed on a sticker; scanning it opens this
locker»), `InventoryItem` мала `minQuantity` («Below this the part joins the
shopping list»). Обидва коментарі описували поведінку, якої жоден екран не
мав.

Але головне було інше: **`Part` не мала жодного зв'язку з деревом вузлів.**
`MeterReading`, `ServiceSchedule` і `ServiceRecord` усі несуть `componentId`,
а `Part` і `InventoryItem` — ні на що. Тобто склад знав, що Jabsco 17937-0001
існує, і ніщо не могло сказати, для чого воно. І сторінка вузла не могла
відповісти на питання, яке власник ставить із **уже розібраним** двигуном:
«а в мене є?»

### `ComponentPart` — many-to-many, не колонка

Обидва напрямки реальні:

* один артикул цинку `Volvo 875812` пасує **і** `anodes_hull`, **і**
  `shaft_anode`;
* одне обслуговування помпи забирає крильчатку **і** прокладку кришки.

Плюс `quantityPerService`: одна крильчатка, але **чотири** аноди й 4,5 літра
оливи. Без цього список покупок просив би по одному всього.

Сутність зареєстровано в `@Database` — і на це є перевірка
`tools/check_entities.py`, бо `@Entity`, про яку Room не знає, не є помилкою
ніде: клас компілюється, таблиця не створюється, екран читає те, чого немає.

### «Докупити» стоїть першим

Це єдина частина складу, яка **терміново**. Власник читає її перед виходом, а
не після того, як лопнув ремінь. Порядок за кількістю: нуль угорі.

Кількість — правий стовпчик моношириною, щоб `0` не могло сховатися між
назвами. Під нею дрібним — мінімум: `0 з 1`.

### Кожен рядок каже, для чого деталь

Артикул сам собою не говорить власнику нічого через три місяці. Тому під
назвою — чипи з вузлами, кожен веде на свою картку. Цинк показує два.

### Кнопка сканера — перша й на всю ширину

На хитавиці власник сканує наліпку відсіку, який перед ним, а не читає список
із п'яти. 56 px — та сама зона досяжності, що й «Зберегти» в аркуші (§8.1.1).
Код наліпки (`FB-A1`) — моношириною: це дані, які зіставляють із наклейкою в
руці, навіть якщо це не число.

### Рядок дефіциту без дієслова

Перша версія казала «1 позиції немає на борту». Для одиниці це правильно
(«немає» керує родовим), для двійки «2 позицій немає» уже спірне — рівно та
пастка узгодження дієслова з числівником, що описана в
[i18n-uk.md §8.3](i18n-uk.md).

Тепер це мітка й число: **«Немає на борту: 1 · Нижче мінімуму: 1»**. Немає
дієслова — немає узгодження, і читається швидше. Ресурс `store_short`
видалено, бо невикористаний ресурс — наступне, що розійдеться.

## 9. ⚠️ Що перевірити в маріні

Це припущення, на яких побудований каркас. Кожне з них можна перевірити за один візит.
Питати не «яку фічу ви хочете», а показувати і просити зробити.

**Про запис робіт**
1. Покажіть, як ви записали **останні пʼять робіт**. Де це зараз лежить фізично?
2. Скільки часу минає між роботою і записом? Записуєте на місці чи ввечері вдома?
3. Коли востаннє забули записати? Що через це сталося?

**Про паспорт вузла — перевірка гіпотези №2 у п.7**
4. Ви памʼятаєте номер масляного фільтра свого двигуна? Де дивитесь, коли треба?
5. Що ви робите, стоячи в магазині й не памʼятаючи, який ремінь потрібен?

**Про лічильник — перевірка можливості OCR**
6. Покажіть, де стоїть лічильник мотогодин. **Сфотографуйте його телефоном.**
   (Дивимось: чи читається взагалі, чи є відблиск, чи можна піднести телефон однією рукою.)
7. Як часто ви на нього дивитесь?

**Про фізичні умови**
8. Дайте телефон у робочих рукавичках і попросіть натиснути кнопку. Що виходить?
9. Чи видно екран на палубі опівдні?
10. Чи є звʼязок у вашому місці стоянки? А на воді?

**Про гроші — найважче питання, ставити останнім**
11. Ви колись платили за застосунок для човна? За який і скільки?
12. Скільки коштувало обслуговування човна цього року загалом?
    (Потрібно, щоб зрозуміти, чи $30 — це справді «rounding error».)

**Про склад**
13. Покажіть, де лежать запчастини. Як ви шукаєте потрібну?
14. Скільки разів купували вдруге те, що вже було на борту?

**Матеріал, який треба винести з візиту**
- Фото: моторний відсік, лічильник, ящики з запчастинами, типовий чек із маріни
- Файл їхньої таблиці, якщо є (найцінніше)
- Фото їхнього паперового журналу, якщо паперовий
